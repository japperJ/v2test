# Debug: Docker compose startup blocked by TypeScript compile failures

## Symptoms (IMMUTABLE — never edit after initial write)
- `docker compose -f infrastructure/docker-compose.yml -f infrastructure/docker-compose.override.yml up -d --build` does not complete successfully.
- Backend Docker build fails during `npm run build` with multiple TypeScript errors.
- Worker Docker build fails during TypeScript compile with ioredis constructor typing error (`Type has no construct signatures`).
- Expected: compose stack builds/starts and smoke endpoints respond from host.

## Current Focus (OVERWRITE — always shows current state)
**Hypothesis:** Resolved — all blockers addressed and compose stack starts; smoke checks pass.
**Testing:** Rebuilt/restarted stack repeatedly with exact command and validated compose status + required host endpoints.
**Evidence so far:** Final compose `up -d --build` succeeds; `/health`, `/documentation`, and MinIO live health endpoint return 200.

## Eliminated Hypotheses (APPEND-ONLY)
### Hypothesis 1: Redis service itself is unreachable from backend container
- **Test:** Executed Redis `PING` from inside `backend` container using `ioredis`.
- **Result:** `PING PONG` succeeded.
- **Conclusion:** Eliminated — infrastructure connectivity is fine.

### Hypothesis 2: Override port remaps replace base ports for compose services
- **Test:** Inspected merged config via `docker compose ... config`.
- **Result:** Both base and override ports were published (`5432` and `5435`, `3000` and `3100`).
- **Conclusion:** Eliminated — override did not replace base ports; it appended, causing host conflicts.

## Resolution (OVERWRITE — filled when fixed)
**Root Cause:** 
1) Worker/backend used direct ioredis constructor patterns that failed type-checking under current module/dependency topology.
2) Backend production `tsc` build included test files, surfacing strict test-only typing errors.
3) JWT request-user typing was augmented on `fastify` instead of `@fastify/jwt`, causing type conflicts.
4) Compose merged port lists from base and override, still binding base host ports (notably `5432`).
5) Backend health Redis probe used ioredis options that created false negatives during initial connection.

**Fix:** 
- Switched worker/backend BullMQ Redis wiring to connection options objects (no direct ioredis client instance required).
- Excluded backend test files from production TypeScript build in `tsconfig.json`.
- Corrected JWT typing augmentation in `authenticate.ts` to `declare module '@fastify/jwt'`.
- Removed base host port publications for `postgres`/`backend` in `docker-compose.yml` so override remaps are authoritative.
- Adjusted health route Redis ping client options to avoid startup false negatives.

**Verification:** 
- `docker compose -f infrastructure/docker-compose.yml -f infrastructure/docker-compose.override.yml up -d --build` completes successfully.
- `docker compose ... ps` shows all required services running; dependencies healthy.
- Host smoke checks:
	- `http://localhost:3100/health` → 200, `{"postgres":"ok","redis":"ok","status":"healthy"}`
	- `http://localhost:3100/documentation` → 200, Swagger UI HTML
	- `http://localhost:9000/minio/health/live` → 200

**Regression Risk:** Low-to-moderate; compose base file no longer publishes backend/postgres host ports by default (intended for this override-based setup), but intra-compose networking remains unchanged.
