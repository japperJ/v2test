# Phase 5 Research: Production Hardening (Geo-fenced multi-site webserver)

This research is scoped to Phase 5 goals:
- rate limiting (different policies for auth/admin/protected)
- OpenAPI/Swagger registration & best practices
- CSP / security headers (re-enable CSP; allow Leaflet CDNs; allow artifact presigned URLs)
- E2E testing with Playwright + CI integration
- environment validation on startup (fail fast)
- multi-stage Docker best practices for Node 22/Fastify
- health checks (liveness/readiness; DB/Redis)
- error response normalization to `{ error, message, statusCode }`
- Vite production build + serving strategy

It is written to align with the current codebase state:
- Backend bootstrapping is centralized in `backend/src/app.ts`.
  - `@fastify/helmet` is registered with `contentSecurityPolicy: false` (CSP currently disabled).
  - `@fastify/jwt` is registered with `secret: process.env.JWT_SECRET!` (no env validation; non-null assertion).
  - No `@fastify/rate-limit` usage and no Swagger registration even though both dependencies are present in `backend/package.json`.
- Health endpoint `GET /health` exists in `backend/src/routes/health.ts` and checks Postgres (`SELECT 1`) but Redis is a placeholder (`checks.redis = 'ok'`).
- `infrastructure/docker-compose.yml` defines service healthchecks and uses `curl http://localhost:3000/health` for the backend.
- CI in `.github/workflows/ci.yml` runs backend unit tests with Postgres+Redis service containers, but there is no E2E job.
- Frontend pulls Leaflet assets from CDNs in `frontend/index.html` and uses OpenStreetMap tiles in `frontend/src/components/GeofenceMap.tsx` (relevant for CSP allowlists).
- Presigned screenshot URLs are generated by `backend/src/routes/artifacts.ts` using AWS SDK v3, and they reference env vars that do **not** match the `.env.example` naming (see “Env validation” section).

---

## Architecture decisions

### Prefer “secure-by-default baseline” + incremental tightening
**Decision:** implement a baseline of “safe defaults” early (env validation, error normalization, readiness checks, security headers) and then iterate.

**Why:** multiple Phase 5 items reinforce each other:
- Env validation reduces “mystery failures” during readiness checks and CI.
- Error normalization improves rate-limit error responses and OpenAPI consistency.
- CSP allowlists are easiest once you know what third-party origins are actually used.

## 1) Rate limiting (Redis-backed)

### Current state
- `@fastify/rate-limit` is listed in `backend/package.json`, but it is not registered in `backend/src/app.ts`.
- Redis is already a dependency in production topology (`infrastructure/docker-compose.yml`) and used by BullMQ elsewhere in the codebase.

### What the plugin supports (verified)
`@fastify/rate-limit` can:
- apply globally or per-route
- use a Redis-backed store by supplying an `ioredis` instance via the `redis` option
- customize response object via `errorResponseBuilder`
- rate-limit 404 handling by attaching a limiter to `setNotFoundHandler`

Source: `@fastify/rate-limit` README (options include `redis`, `keyGenerator`, `errorResponseBuilder`, and 404 preHandler guidance): https://github.com/fastify/fastify-rate-limit

### Recommended policy split (repo-specific)
**A. Auth endpoints** (e.g., `/api/auth/login`, refresh/token endpoints)
- **Goal:** prevent credential stuffing and user enumeration.
- **Recommendation:** low max per IP + (optionally) per username/email.
  - IP-based is supported out of the box.
  - Username/email-based requires custom `keyGenerator` reading from body and/or running in `preHandler` after body parsing.

**B. Protected endpoints** (`/api/protected/*`)
- **Goal:** protect backend + DB from scraping and abusive traffic.
- **Recommendation:** moderate per-IP limits, and consider grouping “expensive” endpoints (geo queries, heavy DB queries) with stricter limits.

**C. Admin endpoints** (`/api/admin/*`)
- **Goal:** prevent brute forcing admin-only actions, but also avoid breaking legitimate admin usage.
- **Recommendation:** key by authenticated principal when possible (e.g., user ID) rather than only IP.
  - `@fastify/rate-limit` supports changing the hook to run after authentication (`hook: 'preHandler'`), and a custom `keyGenerator` (source above).

### Operational considerations
- **trust proxy:** in production the backend will see `X-Forwarded-For` from nginx (`frontend/nginx.conf`). Rate limiting based on IP only works as intended if Fastify’s `trustProxy` is correctly set (`backend/src/app.ts` uses `TRUST_PROXY === 'true'`).
- **failure mode if Redis is down:** the plugin supports `skipOnError`. Decide whether to fail-open (skip limits) or fail-closed (reject traffic) based on your threat model.

## 2) OpenAPI / Swagger wiring

### Current state
- `@fastify/swagger` and `@fastify/swagger-ui` are installed (`backend/package.json`) but not registered (`backend/src/app.ts`).

### Key constraint (verified)
`@fastify/swagger` must be registered **before** routes to ensure route discovery.

Source: `@fastify/swagger` README (“must be registered before any routes”): https://github.com/fastify/fastify-swagger

### Strategy options

#### Option A (recommended if you want docs that don’t rot): dynamic OpenAPI from route schemas
**What this requires:** each route must define `schema` (params/query/body/response) in Fastify route options.

**Zod-friendly approach:** adopt `fastify-type-provider-zod` to:
- use Zod schemas directly for request/response validation
- transform Zod schemas into JSON schema for `@fastify/swagger` via `jsonSchemaTransform`

Source (verified examples):
- `fastify-type-provider-zod` + `@fastify/swagger` integration example (shows `transform: jsonSchemaTransform`): https://github.com/turkerdev/fastify-type-provider-zod

**Reality check for this repo:** the backend currently uses `zod` v3.x (`backend/package.json`). `fastify-type-provider-zod` supports different Zod majors across its own major versions (see its README compatibility table). If you pick this route, pin versions deliberately and plan the migration.

#### Option B: static OpenAPI specification
If route schemas are not ready, `@fastify/swagger` supports a `static` mode that serves an existing OpenAPI/Swagger file.

Source: `@fastify/swagger` README (static mode): https://github.com/fastify/fastify-swagger

**Tradeoff:** lower upfront work, but the spec can drift unless you enforce updates in CI.

### Securing documentation endpoints
- In production: consider protecting Swagger UI behind admin auth, or expose only in non-production environments.
- Hide internal endpoints (health/metrics) with `schema.hide` / hidden tags.

Source: `@fastify/swagger` route hiding guidance: https://github.com/fastify/fastify-swagger

## 3) CSP + security headers

### Current state
- `@fastify/helmet` is registered with CSP disabled: `contentSecurityPolicy: false` in `backend/src/app.ts`.
- Frontend requires third-party origins:
  - Leaflet JS/CSS: `https://unpkg.com` (`frontend/index.html`)
  - Leaflet.draw JS/CSS: `https://cdnjs.cloudflare.com` (`frontend/index.html`)
  - Map tiles: `https://{s}.tile.openstreetmap.org` (`frontend/src/components/GeofenceMap.tsx`)
- Admin screenshot viewing uses presigned URLs from MinIO/S3 via `backend/src/routes/artifacts.ts`. Those URLs will be to your S3/MinIO origin (which may be different between dev/prod).

### What Helmet/Fastify supports (verified)
- `@fastify/helmet` can be enabled globally, disabled globally, or configured per-route via the `helmet` route option.
- CSP nonces are supported.

Source: `@fastify/helmet` README (global control, per-route, CSP nonces): https://github.com/fastify/fastify-helmet

### Recommended CSP approach (repo-specific)
**Baseline CSP (pragmatic):**
- `default-src 'self'`
- `script-src 'self' https://unpkg.com https://cdnjs.cloudflare.com`
- `style-src 'self' https://unpkg.com https://cdnjs.cloudflare.com` (and add `'unsafe-inline'` only if you discover inline styles you can’t remove)
- `img-src 'self' data: https://*.tile.openstreetmap.org <YOUR_S3_OR_MINIO_ORIGIN>`
- `connect-src 'self'` (plus API origin if frontend is served separately)

**MinIO/S3 artifacts:** if the UI loads screenshots by presigned URLs directly, you must allow that origin in `img-src`. Alternatively, proxy artifacts through your backend to keep `img-src 'self'` (more work, but simplifies CSP).

### Swagger UI & CSP integration
`@fastify/swagger` includes guidance for integrating with Helmet so Swagger UI can function under CSP.

Source (verified): `@fastify/swagger` “Integration” section includes a Helmet CSP snippet using `instance.swaggerCSP.script` and `instance.swaggerCSP.style`: https://github.com/fastify/fastify-swagger

## 4) E2E testing with Playwright + CI

### Current state
- Worker already depends on Playwright (`workers/package.json`), but CI has no E2E job.

### Playwright CI guidance (verified)
Playwright recommends:
- installing browsers and dependencies via `npx playwright install --with-deps` in CI
- using `workers: 1` in CI for stability
- uploading the HTML report as an artifact

Source: Playwright CI docs: https://playwright.dev/docs/ci

### Recommended repo approach
**A. Create a dedicated E2E test project** (either in `frontend/` or as a top-level `e2e/`)
- Keep Playwright versions aligned with the browsers it installs.
- Use Playwright’s `webServer` configuration to start servers during tests.

Source: Playwright configuration docs (includes `webServer` usage): https://playwright.dev/docs/test-configuration

**B. CI integration**
- Add a new GitHub Actions job that:
  - brings up required dependencies (Postgres + Redis, and likely MinIO if artifacts are part of E2E flows)
  - builds and runs backend and frontend
  - runs `npx playwright test`
  - uploads `playwright-report/` artifact

**Alternative (containerized CI):** run tests in Playwright’s official Docker image.

Source: Playwright Docker docs: https://playwright.dev/docs/docker

### Known pitfall in this repo (important)
The worker Docker image is based on Alpine (`workers/Dockerfile`) and installs Playwright with `--with-deps`.

Playwright’s Docker docs state Alpine Linux is not supported (due to musl / browser builds), and recommend Ubuntu-based images.

Source: Playwright Docker docs (“Alpine … not supported”): https://playwright.dev/docs/docker

If you reuse Playwright for E2E in CI, prefer Ubuntu runners or the official Playwright Docker image.

## 5) Env validation on startup (fail fast)

### Current state
- Multiple env vars are non-null asserted, e.g. `process.env.JWT_SECRET!` in `backend/src/app.ts` and AWS credentials in `backend/src/routes/artifacts.ts` and `workers/src/s3Client.ts`.
- **Naming mismatch:**
  - `.env.example` files define `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`, `S3_BUCKET` (`backend/.env.example`, `workers/.env.example`).
  - runtime code expects `AWS_ENDPOINT_URL`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, and `S3_BUCKET_NAME` (e.g., `backend/src/routes/artifacts.ts`, `workers/src/s3Client.ts`).

This mismatch is a production foot-gun: the app can “start” but fail only when an artifacts feature is used.

### Recommendations
- Adopt a single canonical env naming scheme and update both code and examples.
  - Practical choice: align to the AWS SDK variable names already used in code.
  - If you keep `S3_*`, map them at startup and log a warning.
- Add strict startup validation (Zod schema is already in dependencies).
  - Validate presence, allowed values (e.g. `TRUST_PROXY`), and minimum secret length.
  - Optionally validate connectivity (DB/Redis) as part of readiness, not startup (to avoid restart loops during dependency warmup).

## 6) Docker hardening (Node 22 / Fastify)

### Current state
- `backend/Dockerfile` is multi-stage (good) but:
  - uses `node:22-alpine` and runs as root by default
  - does not use an init wrapper (PID 1 signal/zombie handling)
- `workers/Dockerfile` installs Playwright twice (builder + production stage), and is also Alpine-based.

### Verified best practices (Node images)
Node Docker best practices recommend:
- using `--init` (Tini) because Node is not designed to run as PID 1
- running as a non-root user (`node` user exists in official images)
- using `CMD ["node", "..."]` instead of `npm start` so signals reach Node

Source: Node docker-node BestPractices (“Handling Kernel Signals”, “Non-root User”, “CMD”): https://github.com/nodejs/docker-node/blob/main/docs/BestPractices.md

### Recommendations (repo-specific)
- Backend image:
  - switch to non-root `USER node` (and ensure `/app` is owned appropriately)
  - consider adding an init wrapper (either in Dockerfile via `tini`/`dumb-init` or at runtime via Docker `--init` / compose)
- Worker image:
  - strongly consider switching away from Alpine and/or basing on the official Playwright image for stability and predictable browser deps.

## 7) Health checks: liveness vs readiness

### Current state
- Only `GET /health` exists.
- It checks Postgres but does not check Redis.
- docker-compose uses `/health` as backend healthcheck.

### Recommendations
- Add a true Redis check (PING) using the same Redis URL used elsewhere.
- Consider splitting endpoints:
  - **liveness**: process is up and event loop healthy (no dependency checks)
  - **readiness**: DB + Redis reachable, and GeoIP DB initialized (since `geoIPService.initialize()` runs at startup)
- Ensure health checks have timeouts (avoid “hung” health endpoints). In Fastify, you can implement timeouts at the driver level (DB/Redis client) and/or via server settings.

## 8) Error response normalization `{ error, message, statusCode }`

### Current state
- Many routes send ad-hoc error objects (commonly `{ error: '...' }`).
- There is no global error handler in `backend/src/app.ts`.

### Why normalize
- Consistent client-side behavior (frontend can reliably display `message` and branch on `statusCode`).
- Easier to wire OpenAPI error responses.
- Aligns with rate limit plugin’s default error response shape.

Verified: `@fastify/rate-limit` default error response includes `statusCode`, `error`, `message`.

Source: `@fastify/rate-limit` README (default 429 payload and `errorResponseBuilder`): https://github.com/fastify/fastify-rate-limit

### Recommended approach
- Add a global `setErrorHandler` that:
  - maps known errors (validation, auth, rate limit) into the normalized shape
  - hides internal error details in production
- Over time, refactor routes to throw errors instead of manually shaping responses, so the handler becomes the single shaping point.

If you adopt `fastify-type-provider-zod`, it includes helpers and examples for customizing schema validation error responses.

Source: `fastify-type-provider-zod` “Customizing error responses”: https://github.com/turkerdev/fastify-type-provider-zod

## 9) Vite production build + serving

### Current state
- Frontend is a Vite SPA served via nginx (`frontend/nginx.conf`) with an `/api/` reverse proxy to backend.

### Verified Vite guidance
- `npm run build` produces a `dist` folder suitable for static hosting.
- `vite preview` is intended for local preview only and is *not* a production server.

Source: Vite static deploy guide (“vite preview … not meant as a production server”): https://vite.dev/guide/static-deploy.html

### Recommendations
- Keep nginx for production serving (good fit for SPA + caching).
- Ensure correct caching:
  - HTML: `Cache-Control: no-cache` (so new deployments update the entrypoint)
  - hashed assets: long cache (immutable)

Vite documents a real-world failure mode where old HTML references deleted chunks after deployment; it suggests `Cache-Control: no-cache` on HTML.

Source: Vite build guide (“Load Error Handling” + caching note): https://vite.dev/guide/build.html

## “Essential” vs “nice-to-have” checklist for Phase 5

**Essential (strongly recommended before production):**
1. Env validation + resolve the S3/AWS env naming mismatch.
2. Real readiness check for DB + Redis (and keep `/health` behavior aligned with docker-compose).
3. Re-enable CSP with a minimal allowlist matching actual CDN usage.
4. Redis-backed rate limiting for auth endpoints (credential stuffing protection).
5. Non-root containers + init/signal handling improvements.
6. Add E2E smoke tests with Playwright in CI (even 2–3 critical flows).
7. Add a global error handler to normalize error responses.

**Nice-to-have / iterative improvements:**
- Full OpenAPI generation from Zod schemas (or static spec initially, then migrate).
- More granular rate limiting by route groupId and authenticated user ID.
- Proxy artifact access through backend to simplify CSP.
- Sharded Playwright E2E runs once the suite grows.
